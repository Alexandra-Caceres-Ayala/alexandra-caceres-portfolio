EVOLUCIÓN: el observatorio que se publica solo

Cómo construí — y opero — una plataforma editorial diaria sobre el ecosistema del dato en español, con un coste de operación cercano a cero.

IA en modo desatendido Python · pandas Altair GitHub Actions & Pages Markdown
Ver la web Repositorio

El problema

Mantenerse al día del ecosistema del dato en español significa revisar decenas de fuentes cada mañana: lanzamientos, actualizaciones de herramientas, movimientos del sector. Quería un observatorio diario y riguroso — pero era una sola persona, cursando un bootcamp intensivo de análisis de datos en paralelo.

Así que la pregunta de diseño no fue «¿puedo publicar un boletín?», sino: ¿puede existir un medio diario cuyo coste de operación sea cercano a cero?

Los requisitos que me impuse

  • Rigor: cada noticia con su fuente verificada y enlazada.
  • Cadencia diaria sostenible en el tiempo — sin depender de mi disponibilidad.
  • Archivo completo consultable: buscador, RSS y etiquetas por herramienta.
  • Coste recurrente ≈ 0, en dinero y en horas.
  • Sin dependencia de plataformas: Git + Markdown como única fuente de verdad.

El pipeline, de la fuente al lector

1

Ingesta y redacción

Un agente de IA en modo desatendido se lanza solo cada mañana: recopila las noticias del día y redacta el borrador, con su fuente verificada en cada pieza. → boletines-crudos/

2

Curación editorial

Del crudo al definitivo: estructura, etiquetas y criterio. El resultado es un archivo Markdown por edición — la única fuente de verdad del sistema. → boletines/

3

Procesamiento

Python normaliza el contenido y extrae las etiquetas por herramienta. importar_boletin.py

4

Análisis y visualización

pandas cuenta menciones por herramienta y Altair dibuja el ranking y su tendencia en el tiempo, adaptado a tema claro y oscuro. graficos.py

5

Publicación

El sitio estático se regenera con SEO, RSS y sitemap, se sube por la API de GitHub y GitHub Actions lo despliega en Pages. Cero pasos manuales. generate_site.py · seo.py · subir_boletin_github.py

Cuatro decisiones técnicas, contadas

1 · Markdown en Git como base de datos. ¿Por qué no una base de datos convencional? Porque un archivo de texto versionado da historial gratis, portabilidad total y cero mantenimiento. Para un archivo editorial, la simplicidad es una decisión de arquitectura, no una carencia.

2 · IA desatendida, criterio humano. El agente redacta cada mañana, pero el sistema le exige una fuente verificable por noticia y la línea editorial está definida por mí. La calidad no se delega: se diseña el proceso para protegerla.

3 · Carga diferida del gráfico (~800 KB). La librería de visualización pesaba ~800 KB y se descargaba en cada visita, la viera el lector o no. La convertí a carga diferida: solo se descarga al desplegar el panel. Un archivo diario debe ser ligero antes que lucido.

4 · Automatizar lo recurrente para proteger lo importante. El ciclo diario no me cuesta horas: me cuesta supervisión. El tiempo liberado va donde más rinde — el análisis y mi formación.

Lo que se rompió (y qué aprendí)

El estreno no fue perfecto. El primer despliegue destapó bugs en el importador, que hubo que corregir sobre la marcha. Y tras un rediseño visual, los lectores seguían viendo la versión antigua del sitio: la caché servía el CSS viejo. De ahí aprendí a versionar los assets (cache-busting).

Un sistema en producción se termina de depurar en producción. Lo importante no es que nada falle nunca — es que el arreglo llegue antes que la siguiente edición. Todo el historial está público en el repositorio.
